## 🛰 Mission: Finora v1: research, council, plan, then a fully working agentic company explorer

Build Finora autonomously, from research to a FULLY WORKING prototype that the human will use every day. A half-done demo does not count.

Finora is a free, open-source, agentic company-intelligence app. Its first and main flow is ONE flow that combines:
- a company explorer: search a company and see everything official data says about it
- agentic search: research agents dig further across registries, filings, courts, sanctions lists and the open web, in parallel, visibly, and end in a sourced verdict

Doing this by hand takes hours; agents do it in minutes. The product should SHOW what agents can do: live parallel work, questions back to the human, citations. More tools come later, so the architecture must carry many tools and pages. Crash monitor (markets) is the second tool.

Scope: USA + Baltics (LT, LV, EE). Market data for Crash monitor.

Read first: CLAUDE.md (hard rules), the main checkout's .local/CONTEXT.md (private context: never quote it publicly; `git worktree list` shows the main checkout), docs/research/00-feasibility.md (hypotheses), docs/design/README.md (the first prototype; it was made without data, so redesign freely), docs/contributing/publishing-checklist.md.

The repo is PUBLIC and its history is permanent. Never name companies, products or people. That covers files, commits, PR text and mission posts. Check every post with `node scripts/guard/guard.mjs text -` before sending. The git hooks and CI guard every commit; never bypass them.

PHASES. The coordinator advances a phase only when its exit criteria are met.

1. DATA RESEARCH (no app code). Data seats call or download every public source for real and record:
- fields
- rows, coverage and freshness
- join keys
- licence, verified on the official page
- keys, limits and cost
- legal constraints

Deliver in docs/research/:
- a source catalog per area
- a DISPLAY MATRIX: each report section and Crash monitor tile, by country, with the sources that fill it and their quality
- a REALITY CHECK: real profiles built for sample entities. Committed reports contain only aggregate fill rates; entity-level output stays in research/.cache/.
- the legal memo

2. COUNCIL SESSION 1: DATA. The council (council + cto seats, advised by legal and designer) decides, for every data item:
- show, show with caveat, hide, or later, and why
- how it appears in the UI
Record this in docs/plan/council/01-data.md, keeping dissent visible.

3. THE PLAN (no app code). It must be exceptionally good: a builder should never have to guess.
- architect: docs/architecture.md plus a slice plan. Each slice gets acceptance criteria, tests, and a demo step.
- designer: DESIGN.md plus screens for every state.
- frontend: component inventory and UI build plan.
- data seats: a loader spec per source.
- data-osint: the agent runtime and tool specs: parallel agents, questions to the human, citations, cost caps.
- docs/plan/prototype.md: what "fully working" means, with daily-use scenarios, a demo script, a risk register, and the test and CI strategy.
- qa reviews the plan; web-qa reviews the mockups in a real browser.

4. COUNCIL SESSION 2: PLAN APPROVAL. Council + cto red-team the whole plan, and it is revised until they approve. Record this in docs/plan/council/02-plan.md. Council approval is the go-ahead to build; the human is informed, not asked.

5. BUILD, slice by slice per the approved plan.
- Foundation first: monorepo, Next.js, design system, lint, typecheck, unit and e2e tests, CI.
- Then data loaders, the entity store, the API and an MCP server, the agent runtime, the explorer + agentic search flow, and Crash monitor.
- Every slice gets tests, a qa review, and a web-qa pass for UI. A MUST-FIX blocks the slice.
- COUNCIL SESSION 3 at each milestone demo: would we use this daily? What's missing? Record in docs/plan/council/.

6. DONE when:
- one documented command runs the app locally with real data for LV, EE, LT and US companies
- the explorer + agentic search flow works end to end with sourced verdicts
- Crash monitor works
- the tests and CI are green
- the council signs off that it is fully working
Then the human merges the hub PR.

ONLY THE HUMAN decides (coordinator: decision-request with a recommendation, asked as early as possible so building never waits):
- the code licence, needed before the first code (AGPL-3.0 recommended)
- spending money: paid APIs, or raising caps or the budget
- publishing anything outside this repo: hosting, domains, accounts
- API keys or accounts the app needs: post a human-task
- the final merge
Everything else is decided by the council and the coordinator.
