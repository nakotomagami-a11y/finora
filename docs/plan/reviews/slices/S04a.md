## legal on Q-3 and the sole-trader guard (2026-11-20)

- **Q-3: the no-hash ruling covers disputes** (legal's reading of its restrictions ruling and council addendum point 5, which says "anywhere"). A person-line dispute targets `{companyEid, itemId, sourceRowId}` or `{companyEid, itemId, role}`; `line_hash` only for company lines; disputes are replayed on every read, and a repair never re-shows a disputed person line.
- **Sole-trader ids:** data-baltics (`eda6908`) found that no Baltic sole trader in the current files carries a personal code as its id (LV: all 89,764 sole-trader rows have a register-issued code; LT individual enterprises 9 digits, EE FIE 8 digits; personal codes 11 digits). Legal keeps the write-time refusal and its test anyway, since a future file could differ. **Coordinator's note for the architect:** check each id against the **personal-code pattern of its own country** (an LV sole trader's 11-digit register code starting with 4, 5 or 6 must not be refused because it resembles an EE or LT personal code; qa raised the same scoping point as early-review #20).

**data-baltics on the per-country guard (`9251108`, `lv-register.md`):** measured on the full LV register, the EE/LT check `isBalticPersonalCode` would refuse **5,431 of 90,961 LV sole-trader register codes (5.97%)** and 16,464 other LV codes. The rule for a sole trader's own id props: **LV** refuses only the LV personal-code formats (11 digits with a valid `DDMMYY` prefix, or a `32` prefix), which no LV register code fits; **EE and LT** refuse an 11-digit value passing `isBalticPersonalCode` (their sole-trader ids are 8 and 9 digits). Tests for S04i: a fixture LV sole trader whose register code passes the EE/LT check loads; one with a `DDMMYY` or `32` id is refused. `findPersonalCodes` stays as is (its 11-digit rule only applies off `COMPANY_ID_PROPS`, qa #20).
