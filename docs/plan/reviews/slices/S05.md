# S05 Latvia loaders: reviews

Owner: data-baltics. In progress (2026-11-22).

## First real-data measurements (data-baltics, `dev-desktop-1`)

The six `lv-ur-*` loaders ran on the real data.gov.lv files through `finora-cli data sync --country lv --profile core`, with one worker and an on-disk store.

| Source | Records written | Sync time |
|---|---|---|
| `lv-ur-register` | 456,358 | 356 s |
| `lv-ur-name-history` | 89,477 | 110 s |
| `lv-ur-equity-capitals` | 141,382 | 136 s |
| `lv-ur-memorandum-dates` | 150,706 (events only) | 115 s |
| `lv-ur-liquidations`, `lv-ur-reorganizations` | 9,650 + 10,198 | 11 + 17 s |

- **Totals:** 747 s for 858k records and 3.1M statements; store file 531 MB.
- **Peak RSS: 1,092 MB** for one worker running seven sources, over P10's 1 GB.
- **Against P10:** P10 says LV is searchable in about 2 min. The register alone takes about 6 min.
- **Where the time goes:**
  - Parsing the 129 MB register takes 2.8 s. Writing takes about 0.78 ms per record on disk (about 20 SQLite statements per record).
  - Caching prepared statements made no difference, and neither did skipping the per-record FTS refresh.

## Rulings (2026-11-22)

**1. First-load fast path.** Built by data-baltics as its own S05 commit, after the architect's design check (coordinator).
- **What changes:** the existing-record lookup and the history snapshot are skipped, and only for a source with no records yet. Records, entities and statements go in as multi-row batch inserts. FTS and trigram are built once at the end, per §3.8.
- **Gates that still run** (legal, qa):
  - personal code and person field;
  - the party gate;
  - HIDE;
  - the lease fence on each batch;
  - the purge-guard counts.
- **Proof:**
  - an identical-rows test between a first load and a per-record load of the same file. It compares records, statements, events, fact reports, withheld rows, drop counts by reason, and the FTS and trigram tables after the final build. It includes a person-bearing source (qa).
  - a byte scan of the data dir after the fast-path load (legal).
  - every S04i test stays green.
- **cto:** confirms the target and the 5-10x estimate.

**2. Memory.** cto and the architect choose one of three options: one source per worker in the lane (7 sequential starts, fine under the V8 note), a memory release between sources, or the fast path bringing the lane under budget.
- S05's acceptance records the LV lane's measured peak RSS at or under 1 GB, with the heap cap below it (qa's SHOULD for 768).
- A worker that runs out of memory ends through the fenced failure path, with no partial person row (legal).

**3. `ParsedEntity.ref`.** A dependent source (former names, capital) attaches to a register entity only through its eid, and carries no person data beyond what the register entity holds. A miss is a counted `entity_missing`, never a created company (legal). The architect reviews it with S05.

**4. An `lv-<code>` value in event data as a reference.** Accepted under the S04i reference rule, on these conditions from legal and qa:
1. **Whole value only.** The value must be exactly `lv-` followed by 11 digits. A free-text value containing such a token keeps the full `freeTextHoldsPersonalCode` scan.
2. **Same three gates as reference props:**
   - a valid or fixture LV register check digit;
   - the eid resolves to a non-Person entity in the store (`isCompanyEid`), or is an entity in the same record;
   - a value whose digits fit the LV personal-code shape (`DDMMYY`, or the `32` prefix) is refused, even with a passing check digit.
3. **No silent loss.** A reference whose target isn't in the store yet is refused and counted (`reference_unresolved`). Either resolve it within the sync, or keep the record out of "unchanged", so the event loads on a later sync once the target exists.
4. **Tests:**
   - the 688-case shape (an LV register code that also passes the EE/LT check), held by the store: kept;
   - the same value, not held: refused and counted;
   - a bad check digit: refused;
   - `lv-` plus an EE personal code: refused;
   - an LV personal-code shape: refused;
   - the token inside free text: scanned;
   - the recovery case from condition 3.
5. **Count after the fix:** any reorganisation event whose eid is a company's own register code is kept.

**5. Natural-person tightening.** Facts and events on an entity the record doesn't carry are checked for natural persons; for example, an LV securing measure on a sole trader is dropped and counted. This is accepted and needs tests only.
