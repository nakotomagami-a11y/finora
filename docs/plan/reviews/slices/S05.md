## Rulings (2026-11-22)

**1. First-load fast path.** Built by data-baltics as its own S05 commit, after the architect's design check (coordinator).
- **What changes:** the existing-record lookup and the history snapshot are skipped, and only for a source with no records yet. Records, entities and statements go in as multi-row batch inserts. FTS and trigram are built once at the end, per §3.8.
- **Gates that still run** (legal, qa):
  - personal code and person field;
  - the party gate;
  - HIDE;
  - the lease fence on each batch;
  - the purge-guard counts.
- **Proof:**
  - an identical-rows test between a first load and a per-record load of the same file. It compares records, statements, events, fact reports, withheld rows, drop counts by reason, and the FTS and trigram tables after the final build. It includes a person-bearing source (qa).
  - a byte scan of the data dir after the fast-path load (legal).
  - every S04i test stays green.
- **cto:** confirms the target and the 5-10x estimate.

**2. Memory.** cto and the architect choose one of three options: one source per worker in the lane (7 sequential starts, fine under the V8 note), a memory release between sources, or the fast path bringing the lane under budget.
- S05's acceptance records the LV lane's measured peak RSS at or under 1 GB, with the heap cap below it (qa's SHOULD for 768).
- A worker that runs out of memory ends through the fenced failure path, with no partial person row (legal).

**3. `ParsedEntity.ref`.** A dependent source (former names, capital) attaches to a register entity only through its eid, and carries no person data beyond what the register entity holds. A miss is a counted `entity_missing`, never a created company (legal). The architect reviews it with S05.

**4. An `lv-<code>` value in event data as a reference.** Accepted under the S04i reference rule, on these conditions from legal and qa:
1. **Whole value only.** The value must be exactly `lv-` followed by 11 digits. A free-text value containing such a token keeps the full `freeTextHoldsPersonalCode` scan.
2. **Same three gates as reference props:**
   - a valid or fixture LV register check digit;
   - the eid resolves to a non-Person entity in the store (`isCompanyEid`), or is an entity in the same record;
   - a value whose digits fit the LV personal-code shape (`DDMMYY`, or the `32` prefix) is refused, even with a passing check digit.
3. **No silent loss.** A reference whose target isn't in the store yet is refused and counted (`reference_unresolved`). Either resolve it within the sync, or keep the record out of "unchanged", so the event loads on a later sync once the target exists.
4. **Tests:**
   - the 688-case shape (an LV register code that also passes the EE/LT check), held by the store: kept;
   - the same value, not held: refused and counted;
   - a bad check digit: refused;
   - `lv-` plus an EE personal code: refused;
   - an LV personal-code shape: refused;
   - the token inside free text: scanned;
   - the recovery case from condition 3.
5. **Count after the fix:** any reorganisation event whose eid is a company's own register code is kept.

**5. Natural-person tightening.** Facts and events on an entity the record doesn't carry are checked for natural persons; for example, an LV securing measure on a sole trader is dropped and counted. This is accepted and needs tests only.

**Additions (legal 7070491772, qa 7070494389):**
- For unresolved references, legal prefers the two-pass resolve within the sync.
- After the fix, data-baltics reports the reorganisation-event count by outcome, as counts only: kept as a company reference, refused as a personal-code shape, refused as unresolved.
- The fast-path byte scan uses a person-bearing fixture source. After it, no file in the data dir holds a fixture personal code or a person row id.

## Architect's design check (7070612640), accepted by legal (7070658489)

**Fast path**
- **When it applies:** the source has no row in `main.records`, checked once inside the first fenced `begin()`.
- **What it skips:** the existing-record lookup and the history snapshot. This is behaviour-neutral on a first load.
- **What it batches:** records, statements, events, reports and withheld rows go in as multi-row inserts. Entity inserts batch too, with `upsertEntity`'s exact conflict semantics. `refreshEntity` runs once, as a set-based pass at the end.
- **What still runs per record, unchanged:** `validateRecord`; `applyGates` (personal code, person field, party gate, HIDE, natural person); the masked hash input; `stage()`; the purge-guard counts; the `begin()` fence; `forgetInterned` on rollback.
- **Must match the per-record path:**
  1. A key repeated within one file is deduped in the batch (last one wins) and counted the same way.
  2. A `search_pending` marker per source: if the sync crashes before the final search pass, boot or the next sync runs the pass first.
- **Tests:**
  - the identical-rows comparison, including captions, FTS and trigram, a person-bearing source and a repeated key;
  - the crash case: kill after one committed batch, then the next sync makes every entity searchable;
  - the data-dir byte scan;
  - every S04i test stays green.

**Memory**
- `18be13d` prints each source's worker heap peak.
- The plan: keep one long-lived worker per lane and re-measure with the fast path. If the LV lane still exceeds 1 GB RSS, start a fresh worker per source, in order.
- The heap cap stays at 768 MB. A source whose heap peak exceeds about 640 MB must stream instead.

**`ParsedEntity.ref`:** `{ eid, ref: true, statements }`, with no identity fields; the strict schema refuses any.
- It attaches statements only. A missing entity is `entity_missing`, counted as skipped.
- Gates read the stored entity's `natural_person` and schema.
- A ref eid counts as a reference only through `isCompanyEid`, never as a same-record eid.
- History includes ref eids.
- **Tests:** a missing eid creates no row; a ref to a sole trader drops personal items; the equity file leaves the register's legal form and person flag unchanged.

**`lv-` event-data reference:** the rule as in item 4 above, with a new drop reason, `reference_unresolved`.
- **Recovery:** instead of a second parse pass, the row hash is salted with a retry marker, so the record is rewritten on the next sync.
- **Legal accepts the marker on three conditions:**
  1. The refused value stays withheld and unshown until it loads.
  2. The `reference_unresolved` count is reported on every sync until it reaches zero.
  3. A test proves the event loads on the next sync after its target appears.
- Reorganisation counts are reported by outcome after the fix.

**qa's conditions on the design (7070680171):**
1. **Retry marker:**
   - A record rewritten only to retry an unresolved reference counts as `reference_retry`, not as "written".
   - A rewrite with identical values emits no history event.
   - Records still unresolved after 3 or more syncs are reported in data status.
2. **`ParsedEntity.ref` to a Person-schema entity:** refused and counted, with nothing attached. The Person case is added to the ref tests.
3. **Fast path, interrupted:** a load cut off after some committed batches takes the per-record path on the next sync. The `search_pending` crash test asserts this, and asserts identical final rows against an uninterrupted fast load of the same file.
4. **Deduped repeated keys:** the drop and skip counts match the per-record path exactly, so the two paths' sync reports are identical.

`18be13d` is closed for qa: 207 of 207 green in 3 runs in a row.

## Security review (coordinator's security-engineer, 2026-11-22, range `2cbc65e..4f16b90`)

Review only. Reproductions ran outside the repo against the repo modules; the existing S05 tests pass (112 of 112). Threat model: LV natural-person data and store integrity, threatened by a crafted or corrupted upstream row, the env config or the network path. 10 findings: 0 critical, 1 high, 4 medium, 5 low. **The high and the four medium are MUST-FIX: they are person-data controls (PS3, PS5, PS7, LAW-LV-OFFICERS) or the ruling S05 must meet.**

**MUST-FIX:**
1. **SEC-1 (high): `LV_PERSON_ROWS` is never read.** `LV_PEOPLE_LOADERS` is built once with the default `names_no_id`, `LOADERS` spreads it, the core worker resolves from `LOADERS`, and `apps/cli/src/env.ts` never reads the variable. Reproduced: with `role_counts` set, the registry's officers parserVersion still ends in `names_no_id`, so a real sync stores officer names. The lawyer fallback switch (LAW-LV-OFFICERS, "no code change") silently does nothing, and an invalid value isn't refused. **Fix:**
   - read and validate the variable in the env loader; an unknown value is a boot error;
   - pass it in the sync job, and have the worker build the officers loader with `lvUrOfficersLoader({ personRows })`;
   - test that a core-worker sync in `role_counts` stores no Person row and no fixture name, and that the parserVersion ends `-role_counts`.
2. **SEC-2: free text in enum columns is stored as-is, so a name can get through in `role_counts`.** An unknown `position` or `governing_body` is counted `unknown_enum` but still stored, and `rights_of_representation_type` is stored raw (`lv-people.ts:180-189`). Reproduced with a fictional name placed in those columns: it was found in `statements.value`. **Fix:** store only values from the closed sets (otherwise `unspecified` or dropped, and counted); check each signing-rights token against a closed set; apply the same rule to the LV enum fields that go into event data (liquidation, reorganisation and securing-measure kinds, sanctions role).
3. **SEC-3: officers in `role_counts` and every members record get the lenient key rule, so a personal code can sit in `line_ids`.** `aboutPeople` is true only when a Person entity is present (`validate.ts:103-107`). Reproduced with a synthetic code that passes both the EE/LT personal-code check and the LV register check. **Fix:** a record is about people when it has a Directorship or Ownership entity, or its field map has a `personal: true` field; test officers (`role_counts`) and members line ids with such a code, each refused as `person_field`.
4. **SEC-4: a `ref`, an event or a report can attach to a Person row, and the gates judge a different entity from the one the store writes.**
   - `existingEntity` and `entityId` resolve Person rows (`store/src/registry.ts`).
   - The gate judges a `ref` by `(country, code)` while the store attaches by eid.
   - `naturalEid` returns "company" for an eid it can't classify.
   - `ref` eids count as same-record eids, contrary to the architect's check.
   - Reproduced with a fake source: a statement and an event were written on a `p-…` row. The LV files can't drive this today, but qa's condition 2 (a ref to a Person is refused, with a test) is unmet.
   - **Fix:** `existingEntity` and `entityId` refuse Person rows and count them; a `ref` eid must equal `${country}-${code}`; `naturalEid` fails closed; drop `ref` eids from `recordEids`; add the Person test.
5. **SEC-5: ruling 4 (an `lv-` reference in event data) is only partly built.** Missing:
   - the `reference_unresolved` and `reference_retry` drop reasons;
   - on the knownCompany path, the whole-value `lv-` + 11-digit check, the check-digit check and the personal-code-shape refusal;
   - correct counting: an unresolved value that fits a personal code is counted `personal_code`, and one that doesn't fit is stored instead of refused;
   - retry: an unchanged file returns "unchanged" without re-parsing, so a refused event is never retried and nothing is reported on every sync;
   - tests: 2 exist, and the ruling lists 7.

   **Fix:** build ruling 4 as recorded above: the three gates, `reference_unresolved`, the salted retry marker with `reference_retry` counted apart, the 3-sync report in data status, the seven tests, and the reorganisation counts by outcome.

**SHOULD-FIX:**
6. SEC-6: `lv-financials.ts` has its own CSV reader (`readTable`) with no field-count or length limits, and quoted multi-line fields misalign rows. Use the formats limits or the streaming `csvRows`, and refuse a line with an odd number of quotes.
7. SEC-7: the fetcher accepts `http:`, and the LV loaders fetch whatever resource URL the portal JSON lists. Refuse non-https resource URLs in the LV loaders. Better, make the fetcher https-only unless a source opts in (architect).
8. SEC-8: the reorganisation `hashInput` uses raw counterparty code columns even when the code is rejected, and hash input is scanned only for records with a Person. Hash the cleaned code, or `""` when it is rejected. Confirm whether `row_hash` is an unsalted digest.
9. SEC-10: fixture and real loaders share source ids and the data dir, so `--profile fixtures` against a real data dir rewrites real LV sources, within the purge guard. Refuse the fixtures profile on a data dir that holds a real core sync, or prefix the fixture source ids (architect).

**For legal:** SEC-9. Foreign holders typed `FOREIGN_ENTITY` and sanctions-link party names are stored by name in every mode, including `role_counts`. Should `role_counts` drop them too?

**Sound:**

## cto: one write path, six fixes (7075394106). Adopted (coordinator)

cto measured the real LV register file (490,539 rows) through the real `runSync` path on `dev-desktop-1`. Six fixes take the register from 549 s to 132 s (4.2x). With the same rows under a new file hash, the sync drops from 165 s to 30 s.

**cto's decision: no second write path.** A separate first-load path would duplicate the gates, refusals, hashing and history code where the legal rules live, and it buys nothing over these fixes. Skipping the lookup or the snapshot saves only microseconds. **This replaces the fast path in item 11 of the fix list.** data-baltics builds the six fixes inside S05, and the architect reviews the store diff.

**The six fixes:**
1. Batch size adapts instead of halving: `clamp(inBatch × maxMs ÷ elapsed, 50, 5000)`. Test: a 1 ms-per-record source keeps about 250 records per batch.
2. A per-connection prepared-statement cache in `store`.
3. Search rows go through a `search_dirty` table, marked in the write transaction. They are rebuilt at sync end in transactions of 5,000, and boot or the next sync finishes any leftover. Captions stay inline (§3.8).
4. `PRAGMA temp_store = MEMORY` in `openStore`.
5. A 64 MB page cache on the sync connection.
6. `writeParsed` compares the record hash before reading the snapshot.

**Memory:**
- The 1,092 MB comes from the parse, not the write path. `csvRows` takes the whole file as one string, which costs about 375 MB on the register.
- Fix: decode in chunks (`TextDecoder` with `stream: true`) and parse from the chunks.
- Annual reports use the streamed artifacts (`9ec97db`).
- data-baltics posts each source's peak (heap, external, RSS).
- Lanes share one process, so S12 measures the process-wide peak.

**S05 targets, measured with `finora-cli data sync` and recorded in `benchmarks.md`:**
1. The LV register is synced and searchable in 150 s or less.
2. All of LV core loads in 5 min or less.
3. Sync worker peak RSS is 1 GB or less, with all LV sources in one worker.
4. Write-transaction p95 is 400 ms or less, and none reaches 5 s.
5. Same rows under a new file hash: the register finishes in 45 s or less, with 0 statement writes.

**`ParsedEntity.ref` condition:** an `entity_missing` skip leaves the content hash unset, so the next run parses again, and the report counts the skips. The register-first `meta.order` test lands with S05.

**The `lv-` event-data question in cto's post** was settled before it (ruling 4 above, plus qa and legal). Only cto's figure is still open: data-baltics reports how many of the 688 refused events point at a stored non-natural company.

**legal (7075401998), on cto's question:** the stricter rule holds, with no register-code exception. An `lv-` value in event data passes only as a typed reference that resolves to a company in the store, not a natural person. The digit-shape check is a second gate, never the only one, because a foreign personal code can fit neither LV shape and still pass the check digit. The 688 events are kept only where the reference resolves to a company that the register loaded first; the rest stay refused and counted. Ruling 4 already says this, and its store-resolution gate is the one that decides.

**Conditions on the single write path (qa 7075412192, legal 7075409028):**
1. **`search_dirty` survives a crash.** The marker persists per source, and boot or the next sync rebuilds while it is set. Test: kill after one committed batch, then every committed entity becomes searchable.
2. **Batches stay safe.** Every batch opens through the fenced `begin()`, and an adaptive batch never grows past the 250 ms bound. Tests: a slow-disk shim, and a takeover between batches that ends `lease_lost` with nothing purged.
3. **Memory counts fully.** The in-memory temp store and the 64 MB cache count against the 1 GB budget. The per-source RSS peak is taken during the purge step too, since the register's staged keys now sit in RAM.
4. **History still runs.** Comparing the hash first never skips history for a changed record. The S04i history tests stay green, plus a case where only a tracked field changes.
5. **Retries are counted.** An `entity_missing` skip with no content hash is counted and retried. Test: the record loads once its register entity exists.
6. **Byte scan.** Legal's scan of the data dir and raw dir runs after a full LV fixture load, in both `role_counts` and `names_no_id`. The statement cache and the search rebuild hold no person value beyond the sync's own memory.

## M1-M5 fixed by the architect `c4ac6cf`, plus `1644fa4`

The gate and store code is the architect's package, so the architect took M1-M5; ingest and store pass 204 of 204. `s05-review.test.ts` reproduces qa's five probes.
- **M1:** a ref to a person or relationship row is dropped (`ref_not_company`), and the store refuses it as well.
- **M2:** `entityByEid` looks a ref up by its eid, and a code mismatch attaches nothing (`ref_mismatch`). A sole trader's own ref gets the natural-person drops.
- **M3:** a ref is never a same-record eid.
- **M4:** an event-data company reference passes only when both its shape and its existence check out. The shape is a public eid by `eidKind`, with a check digit and never the personal-code shape. The record must carry the company, or the store must hold it. `isCompanyEid` refuses relationship rows; person and relationship row ids are refused (`person_field`); a failed check digit is refused (`invalid_code`).
